# Refactor maintainability review

Date: 2026-11-14. Gameplay baseline reviewed: `871d851`.
Scope: all 55 browser/server/API JS/TS modules, their literal imports/re-exports, ESLint structural
metrics, controller composition, shared state, network boundaries and resource teardown. Tests,
generated artifacts and dependencies are outside the product-file inventory.

Policy update: the original 400-line signal used in this snapshot was insufficiently justified.
[ADR 0007](../adr/0007-module-size-threshold.md) compares 200/300/400/600 and adopts 300 code lines
for subsequent reviews. The current report therefore flags 16 modules rather than the original 11;
that increase comes from the policy change, not source growth.

The refactor improves organization, preserves the map/movement baselines and passes CI/Sonar, but
does not finish the modularization. The findings below remain open unless explicitly marked fixed.
This is an architectural review, not a claim that every warning is a defect or every large file
must be split immediately. The [engineering standard](../engineering-standard.md) defines the
measurement policy.

## Prioritized findings

### R1 — High: message payloads are not validated at the gameplay boundary

Status: implemented. Typed gameplay contracts now validate packets before transport dispatch,
forwarding and lobby handshake adoption. Regressions exercise malformed damage/snapshots through
composed applications and verify rejected packets are not forwarded to other peers. Established
valid messages keep their wire representation. This addresses input safety, not anti-cheat authority.

Evidence: [protocol.ts](../../src/network/protocol.ts),
[multiplayer.js](../../src/application/multiplayer.js) and
[remote-player.js](../../src/gameplay/remote-player.js).
`isWireMessage` validates the envelope, while handlers dereference payload fields and consume
numeric snapshots directly. A connected peer's `{ t: 'pdmg', d: null }` passes the envelope check
and causes a `TypeError` in an active-match damage handler. A negative damage amount increases HP.
Both behaviors were reproduced in an isolated application-fixture test during review; no real
network or external players were involved. Authority and identity checks do not validate payloads.

Define typed decoders for gameplay messages, finite vectors, bounded numbers, snapshot lengths and
roster/array limits. Drop malformed packets before any mutation or forwarding to gameplay. Keep the
existing valid wire representation compatible; anti-cheat authority is a separate design concern.
Test malformed payloads through the transport/application boundary, not only the parser in isolation.

### R2 — High: whole-runtime access and callback cycles preserve semantic coupling

Evidence: [application.js](../../src/application/application.js),
[runtime.js](../../src/application/runtime.js), [controls.js](../../src/application/controls.js),
[screens.js](../../src/application/screens.js) and
[multiplayer.js](../../src/application/multiplayer.js).
Controllers receive the whole mutable runtime plus action bags. Screens invoke controls and
multiplayer; multiplayer invokes screens and controls; controls invoke both. Callback wiring avoids
import cycles, but these components still depend on one another's sequencing and shared state.
For example, ending a lobby changes transport, roster, scores, map/session state and UI together.

Separate session commands/read models from presentation and transport adapters. Define the ownership
of transitions such as join/start/leave/migrate, then supply each component a narrow typed contract.
Keep orchestration in a small composition/application layer. A global event bus or more wrapper
files would not by itself solve the shared-state dependency.

### R3 — High: the largest entity classes still combine multiple independent responsibilities

Evidence: [enemies.js](../../src/gameplay/enemies.js),
[player.js](../../src/gameplay/player.js) and [weapons.js](../../src/gameplay/weapons.js).
Enemy creation, targeting, steering, archetype state machines, damage/death and animation still share
one manager. `_think` has cyclomatic complexity 52; `kill` has 39. Player phases are named, but
movement, grapple, grenades, camera feedback, damage and equipment still share one object.
`_updateGrapple` has complexity 37. Gun `update` has complexity 49 and mixes reload/fire state with
view-model animation.

Extract cohesive components with owned state and explicit inputs/results: enemy lifecycle and
archetype behavior, player movement/grapple/grenades, weapon state and presentation. Keep the
existing update order, random draw order, timing and reusable vector allocation where behavior
depends on them. Helpers accepting the entire manager/player would only distribute the original
coupling. Use the recorded movement and composed-session regressions throughout the extraction.

### R4 — Medium: detached scene objects can escape resource disposal

Status: implemented. A typed application-owned registry tracks mesh attachments and shared resource
references, including instance buffers and explicit cached-material leases. Debris transfers retain
existing node ownership; despawn, reset, weapon replacement, pickup collection and fragment expiry
release it. Regressions observe disposal events and shared-material lifetime, including cap eviction.
These checks do not substitute for a real-GPU memory/performance acceptance run.

Evidence: `Player.clearNades`, `EnemyManager.clear`, `RemotePlayer.setWeapon`/`dispose`, and
`Effects.clear`/expired-debris handling. These paths remove dynamically built objects from the
scene without disposing their geometries/materials. Application teardown traverses remaining scene
objects, so it cannot recover resources already detached and no longer retained. Scene emptiness
is not proof that GPU resources were released. The review confirms missing disposal calls; it does
not claim to have measured GPU memory growth on real hardware. Three.js explicitly distinguishes
scene removal from resource disposal in its
[disposal guide](https://threejs.org/manual/pages/how-to-dispose-of-objects.html).

Define ownership and transfer rules for spawned models, shared materials and debris. Dispose unique
resources when their owner retires them, and retain/ref-count resources still used by live siblings.
Add lifecycle regressions observing disposal across reset, despawn, weapon replacement and debris
expiry. Do not blindly dispose a shared enemy material while another fragment still uses it.

### R5 — Medium: a small contract file still names concrete implementations

Evidence: [contracts.ts](../../src/application/contracts.ts). Rendering has an explicit port, but
input, HUD, audio and transport options use concrete class types. Controller action bags and their
runtime parameters remain unchecked JavaScript. `strict` TypeScript configuration does not check
those contracts while `checkJs` is disabled.

Define narrow interfaces from consumer requirements and statically check the composition and its
controllers as they migrate. Preserve simple browser adapters and avoid an interface for every
trivial utility. This work should follow the state-ownership decisions in R2, rather than type the
entire mutable runtime as one oversized interface.

### R6 — Medium: transport lifecycle and lobby discovery are combined and duplicated

Status: implemented. Typed query/discovery owners now share probing, validation, selection,
deadlines, cancellation and connection/listener cleanup. Browsing destroys its temporary endpoint;
quick join explicitly transfers only the selected endpoint to the session. Direct join installs
its session consumer in the welcome event before subsequent packets can arrive. Tests cover late
offers, closed/malformed offers, cancellation and failing adoption/status consumers. The remaining
committed-session adapter is still a size-review candidate; reducing it mechanically is not claimed.

Evidence: [peer-transport.js](../../src/network/peer-transport.js), 694 physical lines.
Connection routing, peer lifecycle, hosting, alias recovery, direct joining, discovery and quick
join share mutable connection/timer state. `quickJoin` and `listLobbies` repeat probe setup,
pending/offer accounting, deadline and teardown logic, with different cleanup responsibilities.

Extract a discovery operation that owns its temporary peer/connections/deadlines and returns
validated offers. Keep committed session connections with the transport. Reuse discovery for list
and quick join, with an explicit adoption step. Preserve cancellation, sender-authority, alias and
stale-connection regression coverage.

### R7 — Medium: presentation boundaries still combine content and stateful systems

Status: implemented. Ink material/shader contracts and palette creation are independent of renderer
lifecycle, with isolated frame uniforms. Audio recipes, synthesis/context ownership, score data,
voice rendering, the music clock and the reel loop are separate collaborators. Effects have separate
particle/fragment simulation, surface decals and pooled rendering owners; recipes receive specific
capabilities. Pre-extraction audio/visual fingerprints preserve schedules, random draw order and
instance-buffer output. See [ADR 0009](../adr/0009-presentation-ownership.md). Audio uses checked
TypeScript contracts; effects remain JavaScript. Real hardware acceptance remains a separate check.

Evidence: [renderer.js](../../src/presentation/renderer.js) has 16 direct product importers, often for
material helpers or palette re-exports rather than renderer lifecycle. Material construction and
mutable shared uniforms live with the full renderer. The palette already has an owning shared
module, but most consumers still import it indirectly.

[audio.js](../../src/presentation/audio.js) combines audio-context lifetime, synthesis primitives,
sound recipes and two musical sequencers. `_musicTick` has cyclomatic complexity 59.
[effects.js](../../src/presentation/effects.js) combines pools, decals, debris physics, particle
simulation and camera shake; `update` has complexity 31.

Separate ink materials/shader contracts from renderer lifecycle; import palette data directly.
Separate audio recipes/score data from context ownership and scheduling. Separate particle/debris
lifetime from effect recipes and pooled rendering. Retain frame-sensitive pooling and avoid
introducing allocations simply to make files shorter. Address resource ownership alongside R4.

### R8 — Fixed in the review tooling: architecture checks had incomplete static scope

The original checker inspected top-level imports/exports under `src` only. It did not enforce
server/API boundaries or inspect literal dynamic imports. The shared analyzer now covers all 55
product modules and these import forms. Regression tests exercise allowed server/API imports,
forbidden dynamic dependencies, missing modules and cycles. Callback/state/computed-import coupling
still requires manual review; the tool does not claim otherwise.

## Order of follow-up work

1. Add validated gameplay-message contracts and resource ownership regressions (R1, R4).
2. Agree on session/state ownership and type the narrow composition ports (R2, R5).
3. Extract player/enemy/weapon behavior and session/discovery operations (R3, R6).
4. Separate presentation content from resource lifetime/scheduling and shared material primitives (R7).
5. Reassess map/model content exceptions and reduce remaining complex functions without editing
   existing map geometry. Review the next measured report before adopting a hard per-module budget.

Keep this sequence on the existing refactor branch with focused commits if implemented together.
The review itself does not mark the open gameplay findings resolved or claim a production release.

## Verification and reproducibility

Run `pnpm architecture` and `pnpm review:structure`. The latter writes the complete current file
inventory and source-located ESLint findings to `reports/`. CI publishes those reports beside LCOV.
Review tooling uses the pinned project dependencies; no extra analysis platform is required.

At `871d851`, [CI](https://github.com/meyer-pidiache/papershooter/actions/runs/43590008126) passed
78 unit/integration tests, all three Chromium smoke tests and all three Docker builds.
[Sonar](https://sonarcloud.io/dashboard?id=meyer-pidiache_papershooter&pullRequest=2) passed with
80.6% new-code coverage, 0.2% duplication, no open bugs/vulnerabilities and 148 code smells in the
PR analysis. Those automated results did not identify R1–R7 as complete architectural findings.
The manual review and the metric report serve different purposes.
